Multi-Layer Context Verification Protocol (5 Independent Layers)
Redundant Verification
🛡️ Why Multi-Layer Verification? (No Single Point of Failure)
Relying on a single verification method (e.g., only reading a text file) is vulnerable to manual file corruption or stale state. Stayflexi cross-verifies context across 5 independent, redundant verification layers:
Layer # Verification Method Operational Mechanism Failure Defense & Self-Healing
Layer 1 Double-Buffered Markdown State Reads `current-state.md`, `project-context.md`, `active-tasks.md`, `decision-log.md`. If 1 file is edited manually, remaining 3 double-buffered files detect state mismatch.
Layer 2 Git Commit Hash & Porcelain Shield Compares commit hash in state files against `git rev-parse HEAD` & `git status --porcelain`. Detects uncommitted local changes or branch drift immediately.
Layer 3 Neo4j Node Freshness Validation Compares node `extractedAt` timestamps against Git `LastModified` commit dates. If `git_modified > extractedAt`, marks `isStale = true` & re-indexes AST nodes.
Layer 4 Graphiti Temporal Rationale Memory Queries Graphiti episodic memory for active Architectural Decision Record (ADR) decisions linked to task ID (`TSK-00130`). Prevents AI from undoing intentional trade-offs (e.g. nullable `customerType` field).
Layer 5 Service Health & Schema Probing Probes ports 5432 (PostgreSQL), 7687 (Neo4j), 6379 (Redis), 9092 (Kafka) & GraphQL supergraph. Auto-starts docker services if ports are down; validates live schema alignment.

Just-In-Time (JIT) Dynamic Phase Loading
Memory Architecture
⚡ Why JIT Selective Loading?
Loading all 12 system phases into LLM context simultaneously creates severe token bloat and context clutter.

Solution: The orchestrator uses **Selective JIT Phase Loading** — phases are loaded and executed dynamically only when specific trigger conditions are met.
🎯 Phase Trigger Matrix
  • Phases 0–3 (Boot & Discovery): Always loaded on initial boot.
  • Phase 4–5 (Memory & GraphQL): Triggered when ADR decisions or API subgraphs are modified.
  • Phase 6 (Browser Intelligence): Triggered JIT ONLY when UI components (src/app/) or user journeys are modified.
  • Phases 7–9 (Impact, Telemetry, Risk): Loaded JIT when Composite Risk Score (CRS) $\ge 30$.
  • Phases 10–12 (Governance & Sync): Loaded JIT at completion gate sign-off.
Realtime Example: Editing a backend controller in booking-service triggers Phase 7 Impact Analysis (Cypher blast radius) but skips Phase 6 Browser Intelligence entirely, saving 40,000 LLM context tokens.
Graphify Deep Dive: Role, Use Case, Why & How
Graph Triad Tools (1/4)
🔮 Core Architectural Role & Primary Use Case
Role: Codebase Knowledge Extractor, Abstract Syntax Tree (AST) Analyzer & Graph-Augmented Generation (GraphRAG) Engine.

Primary Use Case: Scans and converts 1,450+ raw TypeScript/JavaScript source files into structured AST nodes and 500+ modular code communities; enables instant multi-hop caller path searches without reading full raw code files.
❓ WHY We Use Graphify in the Platform
Large Language Model (LLM) prompt contexts cannot read 1,450+ monorepo source files simultaneously without exceeding token memory limits or losing cross-file caller/callee link visibility. Graphify builds a lightweight static code graph with explicit confidence tags (EXTRACTED, INFERRED, AMBIGUOUS).
⚙️ HOW We Use It (Step-by-Step Technical Mechanics)
1. Parses source code into Abstract Syntax Trees (AST) using Tree-sitter.
2. Applies Louvain community detection to group code modules into 500+ communities.
3. Exports static Ontology Studio UI & GraphRAG JSON file (.graphify/graph.json).
4. Executes Breadth-First Search (BFS) and Depth-First Search (DFS) traversals for instant queries.
⚡ Real-Time Operational Example (Stayflexi Monorepo)
Parsed C:\Stayflexi: 9,154 AST nodes, 16,835 dependency edges. Identified God Nodes (handleRouteError - 187 edges, Logger - 155 edges). Executing command graphify query "auth flow" returns multi-hop caller paths across microservices in seconds.
Neo4j Deep Dive: Role, Use Case, Why & How
Graph Triad Tools (2/4)
🌐 Core Architectural Role & Primary Use Case
Role: Structural Reality & Graph Database (DB) Engine (Physical Network Topology).

Primary Use Case: Serves as the structural source of truth for microservices, Application Programming Interface (API) endpoints, repositories, and database tables connected by directed relationship edges.
❓ WHY We Use Neo4j in the Platform
Relational databases and flat files cannot query multi-hop dependency chains efficiently. Neo4j executes Cypher graph traversals to calculate exact Blast Radius (BR) before code edits, detects orphan nodes, and enforces schema sanity invariants ($\text{Neo4j} \equiv \text{Codebase}$).
⚙️ HOW We Use It (Step-by-Step Technical Mechanics)
1. Stores property graph nodes (Service, Endpoint, Repository, DatabaseTable).
2. Enforces Cosine similarity fuzzy duplicate checks ($\ge 0.85$).
3. Auto-repairs graph on file deletion (cascading cleanup).
4. Runs Cypher traversals for risk calculation.
⚡ Real-Time Operational Example (Stayflexi Monorepo)
Running Cypher query: 
MATCH (e:Endpoint {route:'/api/v1/auth/login'})
-[:USES]->(r:Repository)
-[:QUERIES]->(t:DatabaseTable)
RETURN e, r, t
Automatically flags repository queries missing organizationId with a Security Risk (SR) tag.
Graphiti Deep Dive: Role, Use Case, Why & How
Graph Triad Tools (3/4)
🧠 Core Architectural Role & Primary Use Case
Role: Dynamic Temporal Episodic Memory Engine (Context Memory Pack).

Primary Use Case: Stores long-term decision rationale, Architectural Decision Records (ADRs), historical trade-offs, and feature evolution across developer session restarts.
❓ WHY We Use Graphiti in the Platform
LLM chat sessions are stateless; prompt history is erased when a session ends. Standard databases don't track *temporal design rationale* (WHY a trade-off was made). Graphiti prevents the AI from repeating past refactoring mistakes or breaking intentional design constraints.
⚙️ HOW We Use It (Step-by-Step Technical Mechanics)
1. Captures Architectural Decision Records (ADRs) & PR sign-offs.
2. Serializes decision episodes into structured memory packs.
3. Loads memory packs Just-In-Time (JIT) during Phase 0 session boot.
4. Queries past episodes before refactoring code.

Retrieves decision rationale for Pull Request #284 (corporate customerType fields). Reminds LLM that customerType was intentionally made nullable to prevent database migration downtime across 5,000 hotel tenants, avoiding illegal non-nullable refactoring.
