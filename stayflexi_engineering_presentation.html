Multi-Layer Context Verification Protocol (5 Independent Layers)
Redundant Verification
🛡️ Why Multi-Layer Verification? (No Single Point of Failure)
Relying on a single verification method (e.g., only reading a text file) is vulnerable to manual file corruption or stale state. Stayflexi cross-verifies context across 5 independent, redundant verification layers:
Layer # Verification Method Operational Mechanism Failure Defense & Self-Healing
Layer 1 Double-Buffered Markdown State Reads `current-state.md`, `project-context.md`, `active-tasks.md`, `decision-log.md`. If 1 file is edited manually, remaining 3 double-buffered files detect state mismatch.
Layer 2 Git Commit Hash & Porcelain Shield Compares commit hash in state files against `git rev-parse HEAD` & `git status --porcelain`. Detects uncommitted local changes or branch drift immediately.
Layer 3 Neo4j Node Freshness Validation Compares node `extractedAt` timestamps against Git `LastModified` commit dates. If `git_modified > extractedAt`, marks `isStale = true` & re-indexes AST nodes.
Layer 4 Graphiti Temporal Rationale Memory Queries Graphiti episodic memory for active Architectural Decision Record (ADR) decisions linked to task ID (`TSK-00130`). Prevents AI from undoing intentional trade-offs (e.g. nullable `customerType` field).
Layer 5 Service Health & Schema Probing Probes ports 5432 (PostgreSQL), 7687 (Neo4j), 6379 (Redis), 9092 (Kafka) & GraphQL supergraph. Auto-starts docker services if ports are down; validates live schema alignment.

Just-In-Time (JIT) Dynamic Phase Loading
Memory Architecture
⚡ Why JIT Selective Loading?
Loading all 12 system phases into LLM context simultaneously creates severe token bloat and context clutter.

Solution: The orchestrator uses **Selective JIT Phase Loading** — phases are loaded and executed dynamically only when specific trigger conditions are met.
🎯 Phase Trigger Matrix
  • Phases 0–3 (Boot & Discovery): Always loaded on initial boot.
  • Phase 4–5 (Memory & GraphQL): Triggered when ADR decisions or API subgraphs are modified.
  • Phase 6 (Browser Intelligence): Triggered JIT ONLY when UI components (src/app/) or user journeys are modified.
  • Phases 7–9 (Impact, Telemetry, Risk): Loaded JIT when Composite Risk Score (CRS) $\ge 30$.
  • Phases 10–12 (Governance & Sync): Loaded JIT at completion gate sign-off.
Realtime Example: Editing a backend controller in booking-service triggers Phase 7 Impact Analysis (Cypher blast radius) but skips Phase 6 Browser Intelligence entirely, saving 40,000 LLM context tokens.
Codegraph Deep Dive: Role, Use Case, Why & How
Intelligence Layer (1/5)
⚡ Core Architectural Role & Primary Use Case
Role: Sub-Millisecond Code Symbol, AST Call Path & Blast-Radius Engine.

Primary Use Case: Performs instant, index-free lookups of functions, classes, interfaces, callers, dynamic dispatch (React callbacks, saga flows), and covering unit test files directly from a 48 MB local SQLite AST index (.codegraph/codegraph.db).
❓ WHY We Use Codegraph in the Platform
Reading raw files sequentially wastes up to 80% of LLM token budgets and risks blind refactoring when modifying shared packages. Codegraph provides the complete caller hierarchy and blast radius in 1 single sub-millisecond query (codegraph_explore) before any code change is attempted.
⚙️ HOW We Use It (Step-by-Step Technical Mechanics)
1. Real-time background daemon (.codegraph/daemon.pid) watches file changes.
2. Incrementally parses modified TypeScript/JavaScript ASTs into SQLite tables in ~1s.
3. AI executes codegraph_explore <symbol_or_path> to retrieve callers and test suites.
4. Mandated by Phase 0 & Phase 7 Boot Protocols prior to code refactoring.
⚡ Real-Time Operational Example (Stayflexi Monorepo)
Querying codegraph_explore "PricingCalculator computeNightlyRate" returns verbatim source lines, 3 callers across booking-service and ComputeDynamicRate.ts, and auto-links the target unit test suite (PricingCalculator.test.ts) in 30ms without reading raw repository files.
